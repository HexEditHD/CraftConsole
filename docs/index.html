Features

Everything you need to run
a Minecraft server

A complete control panel for your server. Click any feature for what it does, how it works, and — where there is one — what it can't do.

What it does. Four hero tiles — server status, version and uptime; players online versus the server's max; server CPU with a history sparkline; and server memory with a fill meter — plus machine-wide CPU and memory arc gauges and a recent-issues feed.

How it works. Everything pushes over Server-Sent Events, so figures update as they change with no polling or refreshing.

Limits. A figure only appears when it's genuinely knowable — if there's no local process (a server reached over RCON, or one not yet started), CPU, RAM and uptime show "Not available" instead of a misleading zero.

What it does. Live console output with level chips (All / Info / Warn / Error / Debug), a text filter, auto-scroll with a "new output" jump button, coloured chat names, and a command input with /-triggered autocomplete over the vanilla command set plus ↑↓ history.

How it works. Output streams over the same live channel as the dashboard; command history is kept in the browser, so it survives a refresh.

Limits. Over an RCON connection this becomes a transcript of commands and their replies, not a live log — RCON has no access to the server's raw output.

What it does. An online player list with avatar, IP, best-effort geolocation and time joined; kick, ban and ban-IP with an optional reason; banned-player and banned-IP lists with pardon; and a whitelist tab with an enforcement toggle plus add/remove/reload.

How it works. Moderation sends the equivalent server command (kick/ban/whitelist); ban and whitelist entries are read from the server's own files.

Limits. Ban-IP is disabled when a connection can't report a player's IP, rather than guessing. Geolocation calls a third-party service (ipinfo.io) and is best-effort.

What it does. Profiles in two modes — Managed, where the panel launches and owns the process, or Remote, attached over RCON — plus start/stop/restart, a guided server-JAR download (Vanilla, Paper and Purpur auto-download with a version picker, progress and cancel), and Java runtime detection with one-click downloads.

How it works. A Managed profile launches the JAR as a child process and reads its output directly; a Remote profile authenticates over RCON instead.

Limits. One active server at a time.

What it does. Commands, the online player list, and moderation (kick/ban/whitelist) all work exactly as they do for a managed server.

How it works. A Remote profile authenticates over the Source RCON protocol and sends commands over that connection; the password is encrypted at rest, so the panel reconnects after a restart without asking again.

Limits. No log stream, no filesystem, and no process to restart — the config editor, plugin list and Restart are disabled with an explanation rather than failing silently. Player join/leave is polled (roughly every 5s); a "server ready" trigger needs a real log line RCON doesn't have. RCON itself has no encryption of its own — only point it at a server on a trusted network.

What it does. A file tree of the server directory, tabbed editing with dirty-state tracking, and Ctrl+S to save.

How it works. Reads and writes are jailed to the server's own directory — nothing can escape it — and limited to known-safe text formats.

Limits. .yml / .yaml / .json / .txt / .properties / .log only, capped at 2 MB per file, and needs a locally-launched server — not available over RCON.

What it does. Scans the plugins folder and reads metadata straight out of each jar's plugin.yml; disabling moves the jar to plugins/disabled instead of deleting it.

How it works. A disable takes effect after the next restart — the same as if you'd moved the file yourself.

Limits. Needs local file access — not available over RCON.

What it does. Backup job definitions — a name, one or more source paths, a destination and a compression level — run-on-demand with live progress, an archive list per job, and restore into a chosen directory.

How it works. Restoring extracts the archive over the target directory, overwriting only files with matching names; every entry is checked to stay within the target before it's written.

Limits. Restoring requires the server to be stopped first — writing over a live world would just be overwritten by the next autosave.

What it does. Triggers on an interval in seconds, a daily time, a player joining, or the server becoming ready; actions to run a console command, broadcast a message, or restart the server. Tasks can be enabled, disabled, or run on demand.

How it works. Triggers and actions run against whatever server is currently active, managed or RCON alike.

Limits. A trigger or action that can't fire on the current connection — Restart or "server ready" over RCON — shows as disabled with why, rather than sitting there silently never running.

What it does. Distills warnings and errors out of the console stream into a filterable feed (All / Warning / Severe), with a live count badge in the sidebar and a one-click clear.

How it works. Every console line is classified as it streams in, so nothing needs to be searched for after the fact.

Limits. Only sees what the console sees — not populated for a connection with no log stream.

What it does. A single operator password (PBKDF2-SHA256, 210,000 iterations) required for every request once set; server-held sessions; a lockout per IP after 5 failed attempts. Settings also covers console display (timestamps, auto-scroll, buffer size) and per-level colour customisation.

How it works. First run is loopback-only, so setup can't be hijacked over the network even if the panel is bound wider afterwards.

Limits. There's no TLS — use an SSH tunnel or a trusted network to reach the panel from elsewhere.
